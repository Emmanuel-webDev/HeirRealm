HeirRealm — inactivity-triggered release for Gno

If you go quiet, your funds move to who should have them — not to a custodian, not into the void.

Keeper fee: 2%   Recipient: 98%

Live on Onyx (onyx-1): onyx.testnets.gno.land/r/g1pzw2mc795ahjumtmkxjyxhz0awklc3apyfpw9e/heirrealm

1 · Lock & Name Alice names Bob as recipient, sets a 60-second check-in window, funds the vault with 1,000 ugnot.
2 · Check in Alice checks in. The deadline moves forward. Nothing happens — that's the point.
3 · Go quiet Alice stops checking in. The deadline passes. The funds are now claimable.
4 · Keeper triggers Carol, a stranger, calls TriggerRelease. Bob gets 98%, Carol earns 2%.

One primitive, five use cases

  1. Inheritance: Holder dies or loses keys → family receives the funds after the check-in window, with no lawyer or shared seed phrase.
  2. DAO / project treasury succession: Maintainer disappears → treasury moves automatically to a successor or community wallet.
  3. Freelancer / bounty escrow: Client funds a vault for a freelancer and checks in while work continues; if the client vanishes, the freelancer still gets paid 98%.
  4. Time-locked gift / trust: Parent locks funds for a child and checks in while active — moves only when the parent goes quiet.
  5. Dormant / unclaimed funds: Team or project funds return to a community wallet after a year of inactivity instead of sitting dead forever.

The 60-second demo

Run locally with gnodev. Full commands and real outputs: DEMO.md. Verified live on a local chain:

$ gnokey maketx call -func CreateVault -args <bob> -args 60 -send 1000ugnot alice
OK!  (1 int)                                  # vault #1 created
# gnoweb: Vault #1 — active — balance 1000 ugnot — deadline 11:21:59Z

$ gnokey maketx call -func CheckIn -args 1 alice
OK!                                            # deadline moves to 11:22:31Z

... 65 seconds pass, Alice goes quiet ...

$ gnokey maketx call -func TriggerRelease -args 1 carol
OK!  (1078 int64)  (22 int64)                 # 1,100 × 98% / 2%
# events: 1078ugnot → bob (recipient), 22ugnot → carol (keeper)

$ curl http://localhost:8888/r/.../heirrealm
Vault #1 — released — balance 1100 ugnot

Verified split: the vault held 1,100 ugnot after a 100 ugnot top-up. Bob received 1,078 ugnot (98%) and Carol the keeper received 22 ugnot (2%) — confirmed in the transaction events and in both final balances.

What the keeper can and cannot do

ActionAllowed?
Release before the deadlineNo — the call aborts
Redirect funds to themselvesNo — funds go only to the named recipient
Be the owner or the recipientNo — the realm rejects both (and owner != recipient at creation)
Release twiceNo — a released vault is closed forever
Trigger the release after expiryYes — and earn 2% for it

Try it yourself

  1. Install Go + the Gno toolchain (v1.8.0) — see README.md.
  2. cd r/heirrealm && gno test -v ./... — 9 tests, all passing.
  3. gnodev . — then follow DEMO.md step by step.
